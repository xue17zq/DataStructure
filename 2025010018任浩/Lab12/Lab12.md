## 二、简化后的节点结构

### 2.1 只保留三个数据成员（TODO 1）

`binNode.h` 中的节点与课本同名，但被刻意简化。请先读懂这张对比表，它决定了本次所有操作的写法：

| 成员或接口 | 课本中的完整 `BinNode` | 本次的简化节点 | 说明 |
| :--- | :--- | :--- | :--- |
| `data` | 有 | 有（填写） | 元素本身，存取都围绕它进行 |
| `lc` | 有 | 有（填写） | 左孩子，没有孩子时为 `nullptr` |
| `rc` | 有 | 有（填写） | 右孩子，没有孩子时为 `nullptr` |
| `parent` | 有 | **没有** | 无法在 O(1) 时间内回到父节点 |
| `height`、`npl`、`color` | 有 | **没有** | 服务于 AVL、红黑树等平衡结构，本次不涉及 |
| 构造函数、`succ`、`size` 等成员函数 | 有 | **没有** | 本次不添加任何成员函数，留到后续实验 |
| `IsLeaf`、`HasLChild` 等判定宏 | 有（`binnode_macro_basic.h`） | **有**（教师提供） | 课本的版本用到 `parent`，本次给出只依赖 `lc`、`rc` 的版本 |

只填写三条数据成员声明，不要添加构造函数或其他成员函数；这样 `BinNode` 是聚合体，可以直接用花括号依次写出三个成员来建立节点：

```cpp
BinNodePosi x = new BinNode{ch, nullptr, nullptr};   // data、lc、rc 依次给出
```

这里的 `BinNodePosi` 是“节点指针”的别名，就是 `BinNode*`；它的来历见 2.5 节。

### 2.2 没有 parent 的后果：改用“指针槽的引用”

缺少 `parent` 是本次最关键的简化。它带来两个直接后果：

1. **只能自根向下走**，沿孩子指针一步步找，不能像课本那样用 `x->parent` 向上回溯。
2. **删除时不能只拿到“节点本身”**。要摘掉一片叶子，必须修改“父节点持有的那个指针”。本次用**指针槽的引用**（`BinNodePosi&`）解决：查找返回的不是节点指针的值，而是**存放这个指针的那个变量**的引用；改动它，就等于改动父节点的接链关系。`_root` 也是这样一个可以被引用的槽，因此删除根节点不需要特殊处理。

### 2.3 空树、空指针与内存释放的范围

- `BinNodePosi` 是 `BinNode*` 的别名，即“节点位置”。空树用 `nullptr` 表示：`_root == nullptr` 时查找任何元素都落空。
- 新节点的两个孩子指针一律置为 `nullptr`，不会出现未初始化的野指针；取到某个节点后，仍要判断孩子是否存在，不能越过 `nullptr` 继续访问。
- **本次只释放“被删除的那片叶子”**：`remove` 每成功删除一次，就释放摘下来的那一个节点。整棵树的析构、`release`、`clear` 属于后续实验内容，本次不实现，程序结束时树上剩余的节点不会被回收；这一点在报告 6.5 最后一题中讨论。

### 2.4 无序性：没有“左小右大”

本实验**不要求任何有序性**：左子树里的元素可以比根大，右子树的可以比根小，树长成什么样完全由建树时的序列决定。这一条决定了三件事：

| 没有有序性 | 于是…… | 与有序树对照 |
| :--- | :--- | :--- |
| 比较一次无法排除任何一侧子树 | 查找只能**遍历整棵树**，代价 Θ(n) | 有序树每层只走一支，O(h) |
| 找不到“中序后继”这种接替者 | 删除**只允许删叶子**，内部节点一律拒绝 | 有序树两孩子删除用右子树最小者顶替 |
| 改 `data` 不会破坏任何次序 | 修改可以**直接原地改写** | 有序树必须“删旧插新”，否则次序会乱 |

另外，树中仍然**不保存重复元素**：`update` 把旧值改成新值时，如果新值已经在树中，必须拒绝。

### 2.5 `BinNodePosi` 这个名字从哪来

课本里写的是这一行：

```cpp
#define BinNodePosi(T) BinNode<T>*   /* 课本记法：元素类型为 T 的节点指针 */
```

它是一个**宏**，因为课本的节点是模板，同一套代码要服务多种元素类型。本实验只用 `char`，没有模板，所以直接用一个别名：

```cpp
using BinNodePosi = BinNode*;
```

意思完全一样：“元素类型为 char 的节点指针”。相比课本的宏，别名有三个好处：参与类型检查、报错能读懂、能放进其他声明里；宏只是文本替换，写错了只会得到一串莫名其妙的错误。

本次**不要求**你改这个别名，也不要删掉它——`binTree.h` 的声明和 `main.cpp` 都在用它。

## 三、接口约定

### 3.1 类只有一个数据成员，公开四个接口

| 接口 | 作用 | 约定 |
| :--- | :--- | :--- |
| `bool build(const char* seq)` | 建 | 按先序扩展序列建树（`'#'` 空子树、`'\0'` 结束）；空树时成功返回 `true`，树已非空时拒绝返回 `false` |
| `BinNodePosi& search(char e)` | 查 | 遍历整棵树；命中返回保存 `e` 的那一格指针槽，落空返回空槽（槽里是 `nullptr`） |

| `bool update(char oldValue, char newValue)` | 改 | 两个值相等、旧值不存在、新值已存在，三种情况都不修改并返回 `false`；否则返回 `true` |

`private` 区域只有 `BinNodePosi _root = nullptr;` 一个数据成员，外加两个**私有静态递归** `searchIn`、`buildIn`。**不要增加任何数据成员**（计数、高度、父指针、标记等），**也不要增加辅助函数或析构函数**：四个操作各自在自己的函数体内完成。`_root` 必须始终指向真实的树根：建树时写回正确的槽，删叶子时把槽置空。

`public` 区域除上表四个接口外，教师还写好了 `root()`（返回树根）与文件末尾的 `travPre` / `travIn` / `travPost` 三个遍历（直接返回形如 `"ABDECF"` 的序列字符串，空树返回空串）。它们只供 `main` 核对整棵树：**保留、不要改动，也不要据此认为本题要求实现遍历**。

### 3.2 查找为什么返回“指针的引用”（TODO 2）

`search` 的返回类型是 `BinNodePosi&`，即 `BinNode*&`。它返回的不是节点，而是**存放节点指针的那个变量**。以第 3 组测试构造的树为例，先序扩展序列 `"ABD##E##C#F##"` 建出下面这棵树：

```text
          A
         / \
        B   C
       / \    \
      D   E    F
```

在该树上调用 `search`，返回值如下表所示：

| 查找元素 | 访问顺序（先序） | 返回的引用槽 | 槽中的内容 |
| :--- | :--- | :--- | :--- |
| `E` | `A` → `B` → `D` → `E` | 节点 `B` 的 `rc` | 节点 `E`（命中） |
| `F` | `A` → `B` → `D` → `E` → `C` → `F` | 节点 `C` 的 `rc` | 节点 `F`（命中） |
| `X` | 整棵树走完都没找到 | 某个空槽 | `nullptr`（落空） |
| 空树上查找任何元素 | —— | `_root` 自身 | `nullptr`（空树） |

实现上是**遍历**：`searchIn(slot, e)` 先看当前槽是不是空、是不是目标，不是就先递归左子树、再递归右子树，**两支都要走**；命中时把那一格返回。这样返回的引用始终是父节点里真正持有的那一格，树为空时它就是 `_root` 这个成员本身，是合法左值，内容是 `nullptr`。不要返回 `nullptr` 的副本，否则删除时就摘不下来。

### 3.3 这里的查找是遍历，不是下降

遍历要按固定顺序访问到**每一个**节点，代价 Θ(n)，本实验的 `search` 正是这种情况：每层两支都要走，找到就提前返回，找不到就是走完 n 个节点。这与有序树不同——有序树每层只比较一次就能排除一半，访问节点数最多 `h + 1`。

`buildIn` 也是一个递归，但它“遍历”的对象是**序列**而不是树：每读一个元素、建一个节点，代价 Θ(n)，递归深度等于树高。`searchIn` 的递归深度同样等于树高，最坏情况（单链）可以到 n。

### 3.4 建树：先序扩展序列（TODO 3）

`buildIn` 按课本 `CreateBiTree` 的**先序递归**写，只是把“从输入流读一个字符”换成了“从字符串读一个字符”。约定只有两条：

- `'#'` 表示空子树；
- `'\0'`（字符串结尾）表示序列结束。

1. 读到 `'\0'` 返回 `nullptr`（序列用完了）；读到 `'#'` 也返回 `nullptr`（这是一棵空子树）。
2. 否则用这个字符建节点，再**先建左子树、再建右子树**，分别接到 `lc`、`rc` 上。
3. `i` 按引用推进，左右两次递归共用同一个下标；每读一个字符都要**先取出来、再 `++i`**。

以 `"ABD##E##C#F##"` 为例：读到 `A` 建根，接着递归建左子树——读到 `B` 建节点，`B` 的左子树读到 `D`、随后两个 `#` 说明 `D` 没有孩子；`B` 的右子树读到 `E` 和两个 `#`；回到 `A` 建右子树——读到 `C`，`C` 的左子树是 `#`，右子树读到 `F` 和两个 `#`。字符串读完，树就建好了。

`build` 只是外层：**树已非空时返回 `false` 且不破坏原来的树**；空树时把 `i` 置 0 交给 `buildIn`，成功返回 `true`。空串或全是 `'#'` 的串建出的是空树，这种情况同样算成功。

本实验的元素类型固定为 `char`：节点里的 `data` 直接保存那个字符，建树的字符串也不需要任何转换。

### 3.5 删除：只删叶子（TODO 4）

`remove(e)` 先用 `search(e)` 取出 `e` 所在的那一格槽：

| 情况 | 判断 | 处理 |
| :--- | :--- | :--- |
| 元素不存在 | 槽里是 `nullptr` | 返回 `false`，不改动 |
| 不是叶子 | `HasChild(*slot)` 为真 | 返回 `false`，不改动（本实验不处理内部节点） |
| 是叶子 | 槽非空且没有孩子 | `delete` 这个节点，**再把槽写成 `nullptr`**，返回 `true` |

最后那句不能省：只 `delete` 不置空，父节点还指着已经释放的内存，随后任何一次遍历都会踩到野指针——这正是 6.6 要验证的实验。

### 3.6 修改：原地改 `data`（TODO 5）

无序树没有要维持的次序，所以 `update` 可以直接改写节点里的 `data`：先排除三种不该改的情况（两个值相等、旧值不存在、新值已存在），再 `search(oldValue)` 拿到槽，写 `slot->data = newValue` 即可。树的结构、节点位置都不变。

这一点和有序树正好相反：有序树里把 `60` 改成 `90` 会让右子树比根还小，只能“删旧插新”；无序树没有这个约束，但**仍然不允许出现重复元素**，所以“新值已存在”那一条必须检查。

| `buildIn` / `build`（`TODO 3`） | `build` 判 `_root` 是否为空，空树时把 `i` 置 0 交给 `buildIn`；`buildIn` 用 `new BinNode{ch, nullptr, nullptr}` 建节点并递归接 `lc`、`rc` | 按先序扩展序列建出整棵树并写回 `_root`；树已非空时返回 `false` 且不破坏原树 |
| `remove`（`TODO 4`） | 复用 `search` 取槽、用 `HasChild(*slot)` 判叶子，`delete` 后把槽写成 `nullptr` | 成功删除一片叶子返回 `true`；元素不存在或不是叶子返回 `false` 且不动树 |
| `update`（`TODO 5`） | 复用两次 `search`：一次定位旧值取槽，一次确认新值不存在 | 原地把命中节点的 `data` 改写为新值；两值相等、旧值不存在、新值已存在三种情况返回 `false` 且树不变 |

回答下面三个问题，每题两三句话：

1. 为什么 `search` 返回 `BinNodePosi&` 而不是 `BinNodePosi`？`remove` 中如何利用这个引用？

> `search` 返回 `BinNodePosi&`（即 `BinNode*&`）而不是节点指针的值，是因为没有 `parent` 时，只有拿到"存放这个指针的那个变量"的引用，才能改到父节点真正持有的那一格。`remove` 正是靠它：`BinNodePosi& slot = search(e);` 之后 `delete slot; slot = nullptr;`——把 `slot` 写成空就是直接把父节点的 `lc`/`rc`（或 `_root`）这一格清空，叶子才被真正摘下来。

2. 树为空时 `search(e)` 返回什么？为什么它仍然是一个合法的引用？

> 树为空时 `search(e)` 走 `searchIn(_root, e)`，第一句 `slot == nullptr` 命中，返回的就是成员 `_root` 本身这一格。`_root` 是 `BinTree` 的左值数据成员，对它取引用完全合法，槽里的内容恰为 `nullptr`，因此调用者用"槽里是否为 `nullptr`"就能判定落空，且不会越界访问任何节点。

3. 如果把 `remove` 写成只 `delete` 节点、忘记把槽置空，会发生什么？请结合“父节点还指着已释放节点”说明。

> 若只 `delete` 而忘记把槽置空，父节点的那个 `lc`/`rc`（或 `_root`）仍指向已经被释放的内存，成为野指针。随后任何一次 `travPre/travIn/travPost`、`search`、`HasChild` 都会顺着这条野指针解引用已回收的对象，造成 use-after-free——轻则读到垃圾字符使遍历序列错乱，重则崩溃。ASan 会把它报成 heap-use-after-free。

### 6.2 建树过程追踪

对序列 `"ABD##E##C#F##"`（`#` 表示空子树）逐行填写：

| 读到的元素 | 动作 | 执行后的 i |
| :--- | :--- | :---: |
| `A` | 读到 `A`，建根节点，`i` 由 0 推进到 1，随后递归建其左子树 | 1 |
| `B` | 读到 `B`，建为 `A` 的左孩子，`i` 推进到 2，再递归建 `B` 的左子树 | 2 |
| `D` | 读到 `D`，建为 `B` 的左孩子，`i` 推进到 3，再递归建 `D` 的左子树 | 3 |
| `#` | 读到第一个 `#`，`i` 推进到 4，说明 `D` 的左子树为空，返回 `nullptr` | 4 |
| `#` | 读到第二个 `#`，`i` 推进到 5，说明 `D` 的右子树为空，`D` 成为叶子并返回 | 5 |
| `E` | 读到 `E`，建为 `B` 的右孩子，`i` 推进到 6，随后再读两个 `#` 令 `E` 成为叶子 | 6 |

然后回答：

1. 按这个序列建出的树画出来（用文字或字符图均可），并指出根节点的元素与叶子节点。

> 建出的树（根 `A`）：
>
> ```text
>           A
>          / \
>         B   C
>        / \    \
>       D   E    F
> ```
>
> 根节点是 `A`；叶子节点是 `D`、`E`、`F`（`C` 只有右孩子 `F`，本身不是叶子；`B` 有两个孩子）。

2. 如果序列写成 `"ABD##E##C###"`（把 `F` 换成 `#`），树会变成什么样？哪几个节点消失？

> 把 `F` 换成 `#`（`"ABD##E##C###"`）后，`C` 的右子树被当成空子树，节点 `F` 整个消失，`C` 变成一个没有孩子的叶子。整棵树变为 `A(B(D,E),C)`，节点数由 6 减到 5，先序序列由 `ABDECF` 变成 `ABDEC`，消失的节点只有 `F`。

3. 如果序列少写一个 `#`（字符串变短），建树会怎样？为什么 `buildIn` 要先判断 `'\0'`？

> 少写一个 `#`（字符串变短，如 `"ABD##E##C#F#"`）时，`buildIn` 在给某个孩子取字符时会先读到 `'\0'`，于是把这棵子树当作空子树返回 `nullptr`，递归就此收敛，最终建出一棵结构上"提前收口"的树（本例中 `F` 的孩子都成空，恰好与完整序列同形），并且**不报错**、`build` 仍返回 `true`。`buildIn` 必须先判 `'\0'`：一是防止读越字符串末尾造成越界访问，二是让递归在序列耗尽时有确定的空出口，否则会无限递归或在随机内存上建出垃圾节点。

### 6.3 删除过程追踪

先填写三种情况的处理方式：

| 情况 | 判断条件 | 处理 | 返回值 |
| :--- | :--- | :--- | :--- |
| 元素不存在 | `search(e)` 返回的槽里是 `nullptr` | 不做任何改动 | `false` |
| 不是叶子 | 槽非空但 `HasChild(*slot)` 为真 | 不做任何改动，保留原树 | `false` |
| 是叶子 | 槽非空且 `IsLeaf(*slot)`（无左、右孩子） | `delete` 该节点，再把这一格槽写成 `nullptr` | `true` |

再以 6.2 建出的树为起点，依次执行下列删除，逐行填写：

| 被删元素 | 属于哪种情况 | 删后该位置的内容 | 删除后整棵树的先序序列 |
| :--- | :--- | :--- | :--- |
| `D` | 是叶子（`D` 无孩子） | `B` 的左孩子这一格由节点 `D` 变为 `nullptr` | `ABECF` |
| `B` | 不是叶子（`B` 仍有右孩子 `E`），拒绝 | `B` 所在格仍指向节点 `B`，整树未改动 | `ABECF` |
| `A` | 不是叶子（根 `A` 有孩子），拒绝 | `_root` 仍指向节点 `A`，整树未改动 | `ABECF` |
| `F` | 是叶子（`F` 左右均为 `#`） | `C` 的右孩子这一格由节点 `F` 变为 `nullptr` | `ABEC` |
| 再删一次 `F` | 元素不存在（`F` 已被删除） | `search` 落空，返回内容为 `nullptr` 的空槽，树不变 | `ABEC` |

然后回答：

1. 为什么无序树不能像有序树那样用“右子树最小者”顶替被删节点？

> 有序树能用"右子树最小者（中序后继）"顶替，是因为它靠这个后继同时维持二叉搜索次序：顶替后左小右大不被破坏。无序树没有任何"次序"可维持，也根本没有"中序后继即接替者"的语义——把谁顶上来都不比谁更合适，还会打乱建树时形成的形状。所以本实验直接规定只删叶子，内部节点一律拒绝，从而回避"谁来顶替"这个无解的问题。

2. 删除一片叶子时，`search` 返回的那个引用起了什么作用？如果只拿到节点指针会怎样？

> 删叶子时 `search` 返回的引用正是"父节点（或 `_root`）持有的那一格指针"，`remove` 借它先 `delete` 节点再 `slot = nullptr`，把父节点对应一侧接链清空。若 `search` 只返回节点指针（值），删除后就无法回写父节点的那一格：没有 `parent` 又拿不到槽，父节点仍指向已释放内存，变成野指针。

3. 如果要求必须能删内部节点，至少需要额外的什么信息或什么约定？举一种可行做法并说明代价。

> 要能删内部节点，至少需要额外的结构信息或一条约定。可行做法之一是给节点补一个 `parent` 指针（课本 `BinNode` 就有）：删除时用 `x->parent` 找到父亲，把父亲指向 `x` 的那一侧改接到 `x` 的（唯一）孩子上。代价是每个节点多存一个指针（空间 Θ(n)），且建树/改接都要同步维护 `parent`；若节点有两个孩子，无序树里没有天然的接替者，还需另定"用某个后代顶替"的约定，代价更大。

### 6.4 复杂度

按本实验的实现分析；视一次元素比较、一次指针赋值、一次节点申请与释放为常数开销。令 `n` 为树中节点数，`h` 为树高。

| 项目 | 复杂度 | 简要理由 |
| :--- | :--- | :--- |
| `build()` 的时间（按 `n`） | Θ(n) | 建树时每个节点恰好创建一次、序列每个非 `#` 字符读一次，共 n 次常数开销 |
| `buildIn()` 的递归深度（按 `h`） | Θ(h)（最坏 Θ(n)） | 递归沿树的一条根到叶路径展开，深度等于树高；单链时树高为 n |
| `search()` 最坏情况的时间 | Θ(n) | 无序树没有可排除的一侧，最坏要访问全部 n 个节点才落空 |
| `search()` 在平衡的树上平均要访问多少个节点 | Θ(n)，约 n/2 个 | 即使树平衡也不能像有序树那样剪枝，命中位置在先序遍历中平均落在一半处 |
| `remove()` 的时间 | Θ(n) | 一次 `search` 遍历为 Θ(n)，判叶子与摘链为 O(1)，合起来 Θ(n) |
| `update()` 的时间 | Θ(n) | 至多做两次 `search`（定位旧值、检查新值），每次 Θ(n)，改写本身 O(1) |
| 存放 `n` 个元素的树占用的空间 | Θ(n) | n 个节点各含 `data`、`lc`、`rc` 为 Θ(n)，另加递归栈最坏 Θ(h) ⊆ Θ(n) |

### 6.5 讨论

用自己的话回答，每题两三句话：

1. 本实验为什么“查找必须遍历”？请举一个**必须**借助遍历才能完成的任务，并说明原因。

> 无序树不保证"左小右大"，比较一次只能判断当前节点是不是目标，无法据此排除任何一侧子树，所以查找必须把整棵树走一遍（Θ(n)）。一个**必须**靠遍历才能完成的任务例子：判断某个元素是否存在，或像 `update` 那样检查"新值是否已在树中"——只要不能凭大小关系剪枝，就只能逐个节点比对，最坏访问全部 n 个节点。

2. 为什么无序树只允许删叶子？对照有序树的三种删除情况，说明差别来自哪里。

> 有序树删除分三种（叶子直接删、单孩子接位、双孩子用中序后继顶替），三种都能在维持 BST 次序的前提下把节点摘干净。无序树没有"后继/前驱"这种能同时保住结构的接替者，内部节点一旦被删，两棵子树没有合法的重接依据，次序与形状都会失控。差别正来自"有无有序性"：有序性提供了可用来顶替与重接的规则，没有它就只能把删除限制在最简单的叶子情形。

3. `update` 在无序树里可以直接改 `data`，在有序树里却必须“删旧插新”。请举例说明有序树直接改会破坏什么。

> 有序树（BST）里把节点的 `data` 直接改写会破坏"左小右大"的不变式。例如一棵以 `60` 为根、右子树含 `90` 的树，若把根 `60` 原地改成 `90`，就出现"根比右子树某个还大的节点…根=90 与右子树 90 相等/更大"，更典型的是把左子树里 `50` 改成 `100`：这个 100 仍挂在根的左侧，违反"左子树全部小于根"，之后按 BST 规则的查找、插入、删除全部失效。所以有序树必须"删旧插新"，让新值按规则重新落到正确位置。

4. 先序扩展序列为什么能唯一确定一棵二叉树？如果只给中序序列、或只给先序序列，还能不能唯一确定？

> 先序扩展序列把"空子树"也写成 `#`，于是"根—左—右"每访问一个真实节点都能明确知道它的左右子树边界，整棵二叉树被逐层唯一展开，能唯一确定一棵树。若只给中序序列，无法确定根，故不能唯一确定；只给（普通、不带 `#` 的）先序序列同样不能唯一确定——只有"先序 + 中序"或"后序 + 中序"这样带一条中序的组合，才因为中序能划出左右子树范围而唯一确定。

5. 本次没有实现析构函数，程序结束时树上剩余的节点不会被释放。这会在什么场景下成为问题？如果要补上，可以怎样写（说明思路即可，不必给出代码）？

> 本次没有析构，程序退出时只剩根指针能触达的那部分被操作系统统一回收，但若这棵树是某个长生命周期对象的一部分、或一棵树被反复"换建树"，前一次建的节点再也无人引用却未被 `delete`，就会持续泄漏内存，长跑程序里迟早耗尽。补法是加析构函数：以后序（后序）顺序 `destroyTree(_root)` 递归地先释放左右子树、再 `delete` 当前节点，最后把 `_root` 置 `nullptr`；这样保证释放父节点前孩子已断开，不会留下野指针。
