## 二、简化后的节点结构

### 2.1 只保留三个数据成员（TODO 1）

`binNode.h` 中的节点与课本同名，但被刻意简化。请先读懂这张对比表，它决定了本次所有操作的写法：

| 成员或接口 | 课本中的完整 `BinNode` | 本次的简化节点 | 说明 |
| :--- | :--- | :--- | :--- |
| `data` | 有 | 有 | 元素本身，存取都围绕它进行 |
| `lc` | 有 | 有 | 左孩子，没有孩子时为 `nullptr` |
| `rc` | 有 | 有 | 右孩子，没有孩子时为 `nullptr` |
| `parent` | 有 | **没有** | 无法在 O(1) 时间内回到父节点 |
| `height`、`npl`、`color` | 有 | **没有** | 服务于 AVL、红黑树等平衡结构，本次不涉及 |
| 构造函数、`succ`、`size` 等成员函数 | 有 | **没有** | 本次不添加任何成员函数，留到后续实验 |
| `IsLeaf`、`HasLChild` 等判定宏 | 有（`binnode_macro_basic.h`） | **有**（教师提供） | 课本的版本用到 `parent`，本次给出只依赖 `lc`、`rc` 的版本 |

只填写三条数据成员声明，不要添加构造函数或其他成员函数；这样 `BinNode` 是聚合体，可以直接用花括号依次写出三个成员来建立节点：

```cpp
BinNodePosi x = new BinNode{ch, nullptr, nullptr};   // data、lc、rc 依次给出
```

这里的 `BinNodePosi` 是“节点指针”的别名，就是 `BinNode*`；它的来历见 2.5 节。

### 2.2 没有 parent 的后果：改用“指针槽的引用”

缺少 `parent` 是本次最关键的简化。它带来两个直接后果：

1. **只能自根向下走**，沿孩子指针一步步找，不能像课本那样用 `x->parent` 向上回溯。
2. **删除时不能只拿到“节点本身”**。要摘掉一片叶子，必须修改“父节点持有的那个指针”。本次用**指针槽的引用**（`BinNodePosi&`）解决：查找返回的不是节点指针的值，而是**存放这个指针的那个变量**的引用；改动它，就等于改动父节点的接链关系。`_root` 也是这样一个可以被引用的槽，因此删除根节点不需要特殊处理。

### 2.3 空树、空指针与内存释放的范围

- `BinNodePosi` 是 `BinNode*` 的别名，即“节点位置”。空树用 `nullptr` 表示：`_root == nullptr` 时查找任何元素都落空。
- 新节点的两个孩子指针一律置为 `nullptr`，不会出现未初始化的野指针；取到某个节点后，仍要判断孩子是否存在，不能越过 `nullptr` 继续访问。
- **本次只释放“被删除的那片叶子”**：`remove` 每成功删除一次，就释放摘下来的那一个节点。整棵树的析构、`release`、`clear` 属于后续实验内容，本次不实现，程序结束时树上剩余的节点不会被回收；这一点在报告 6.5 最后一题中讨论。

### 2.4 无序性：没有“左小右大”

本实验**不要求任何有序性**：左子树里的元素可以比根大，右子树的可以比根小，树长成什么样完全由建树时的序列决定。这一条决定了三件事：

| 没有有序性 | 于是…… | 与有序树对照 |
| :--- | :--- | :--- |
| 比较一次无法排除任何一侧子树 | 查找只能**遍历整棵树**，代价 Θ(n) | 有序树每层只走一支，O(h) |
| 找不到“中序后继”这种接替者 | 删除**只允许删叶子**，内部节点一律拒绝 | 有序树两孩子删除用右子树最小者顶替 |
| 改 `data` 不会破坏任何次序 | 修改可以**直接原地改写** | 有序树必须“删旧插新”，否则次序会乱 |

另外，树中仍然**不保存重复元素**：`update` 把旧值改成新值时，如果新值已经在树中，必须拒绝。

### 2.5 `BinNodePosi` 这个名字从哪来

课本里写的是这一行：

```cpp
#define BinNodePosi(T) BinNode<T>*   /* 课本记法：元素类型为 T 的节点指针 */
```

它是一个**宏**，因为课本的节点是模板，同一套代码要服务多种元素类型。本实验只用 `char`，没有模板，所以直接用一个别名：

```cpp
using BinNodePosi = BinNode*;
```

意思完全一样：“元素类型为 char 的节点指针”。相比课本的宏，别名有三个好处：参与类型检查、报错能读懂、能放进其他声明里；宏只是文本替换，写错了只会得到一串莫名其妙的错误。

本次**不要求**你改这个别名，也不要删掉它——`binTree.h` 的声明和 `main.cpp` 都在用它。

## 三、接口约定

### 3.1 类只有一个数据成员，公开四个接口

| 接口 | 作用 | 约定 |
| :--- | :--- | :--- |
| `bool build(const char* seq)` | 建 | 按先序扩展序列建树（`'#'` 空子树、`'\0'` 结束）；空树时成功返回 `true`，树已非空时拒绝返回 `false` |
| `BinNodePosi& search(char e)` | 查 | 遍历整棵树；命中返回保存 `e` 的那一格指针槽，落空返回空槽（槽里是 `nullptr`） |

| `bool update(char oldValue, char newValue)` | 改 | 两个值相等、旧值不存在、新值已存在，三种情况都不修改并返回 `false`；否则返回 `true` |

`private` 区域只有 `BinNodePosi _root = nullptr;` 一个数据成员，外加两个**私有静态递归** `searchIn`、`buildIn`。**不要增加任何数据成员**（计数、高度、父指针、标记等），**也不要增加辅助函数或析构函数**：四个操作各自在自己的函数体内完成。`_root` 必须始终指向真实的树根：建树时写回正确的槽，删叶子时把槽置空。

`public` 区域除上表四个接口外，教师还写好了 `root()`（返回树根）与文件末尾的 `travPre` / `travIn` / `travPost` 三个遍历（直接返回形如 `"ABDECF"` 的序列字符串，空树返回空串）。它们只供 `main` 核对整棵树：**保留、不要改动，也不要据此认为本题要求实现遍历**。

### 3.2 查找为什么返回“指针的引用”（TODO 2）

`search` 的返回类型是 `BinNodePosi&`，即 `BinNode*&`。它返回的不是节点，而是**存放节点指针的那个变量**。以第 3 组测试构造的树为例，先序扩展序列 `"ABD##E##C#F##"` 建出下面这棵树：

```text
          A
         / \
        B   C
       / \    \
      D   E    F
```

在该树上调用 `search`，返回值如下表所示：

| 查找元素 | 访问顺序（先序） | 返回的引用槽 | 槽中的内容 |
| :--- | :--- | :--- | :--- |
| `E` | `A` → `B` → `D` → `E` | 节点 `B` 的 `rc` | 节点 `E`（命中） |
| `F` | `A` → `B` → `D` → `E` → `C` → `F` | 节点 `C` 的 `rc` | 节点 `F`（命中） |
| `X` | 整棵树走完都没找到 | 某个空槽 | `nullptr`（落空） |
| 空树上查找任何元素 | —— | `_root` 自身 | `nullptr`（空树） |

实现上是**遍历**：`searchIn(slot, e)` 先看当前槽是不是空、是不是目标，不是就先递归左子树、再递归右子树，**两支都要走**；命中时把那一格返回。这样返回的引用始终是父节点里真正持有的那一格，树为空时它就是 `_root` 这个成员本身，是合法左值，内容是 `nullptr`。不要返回 `nullptr` 的副本，否则删除时就摘不下来。

### 3.3 这里的查找是遍历，不是下降

遍历要按固定顺序访问到**每一个**节点，代价 Θ(n)，本实验的 `search` 正是这种情况：每层两支都要走，找到就提前返回，找不到就是走完 n 个节点。这与有序树不同——有序树每层只比较一次就能排除一半，访问节点数最多 `h + 1`。

`buildIn` 也是一个递归，但它“遍历”的对象是**序列**而不是树：每读一个元素、建一个节点，代价 Θ(n)，递归深度等于树高。`searchIn` 的递归深度同样等于树高，最坏情况（单链）可以到 n。

### 3.4 建树：先序扩展序列（TODO 3）

`buildIn` 按课本 `CreateBiTree` 的**先序递归**写，只是把“从输入流读一个字符”换成了“从字符串读一个字符”。约定只有两条：

- `'#'` 表示空子树；
- `'\0'`（字符串结尾）表示序列结束。

1. 读到 `'\0'` 返回 `nullptr`（序列用完了）；读到 `'#'` 也返回 `nullptr`（这是一棵空子树）。
2. 否则用这个字符建节点，再**先建左子树、再建右子树**，分别接到 `lc`、`rc` 上。
3. `i` 按引用推进，左右两次递归共用同一个下标；每读一个字符都要**先取出来、再 `++i`**。

以 `"ABD##E##C#F##"` 为例：读到 `A` 建根，接着递归建左子树——读到 `B` 建节点，`B` 的左子树读到 `D`、随后两个 `#` 说明 `D` 没有孩子；`B` 的右子树读到 `E` 和两个 `#`；回到 `A` 建右子树——读到 `C`，`C` 的左子树是 `#`，右子树读到 `F` 和两个 `#`。字符串读完，树就建好了。

`build` 只是外层：**树已非空时返回 `false` 且不破坏原来的树**；空树时把 `i` 置 0 交给 `buildIn`，成功返回 `true`。空串或全是 `'#'` 的串建出的是空树，这种情况同样算成功。

本实验的元素类型固定为 `char`：节点里的 `data` 直接保存那个字符，建树的字符串也不需要任何转换。

### 3.5 删除：只删叶子（TODO 4）

`remove(e)` 先用 `search(e)` 取出 `e` 所在的那一格槽：

| 情况 | 判断 | 处理 |
| :--- | :--- | :--- |
| 元素不存在 | 槽里是 `nullptr` | 返回 `false`，不改动 |
| 不是叶子 | `HasChild(*slot)` 为真 | 返回 `false`，不改动（本实验不处理内部节点） |
| 是叶子 | 槽非空且没有孩子 | `delete` 这个节点，**再把槽写成 `nullptr`**，返回 `true` |

最后那句不能省：只 `delete` 不置空，父节点还指着已经释放的内存，随后任何一次遍历都会踩到野指针——这正是 6.6 要验证的实验。

### 3.6 修改：原地改 `data`（TODO 5）

无序树没有要维持的次序，所以 `update` 可以直接改写节点里的 `data`：先排除三种不该改的情况（两个值相等、旧值不存在、新值已存在），再 `search(oldValue)` 拿到槽，写 `slot->data = newValue` 即可。树的结构、节点位置都不变。

这一点和有序树正好相反：有序树里把 `60` 改成 `90` 会让右子树比根还小，只能“删旧插新”；无序树没有这个约束，但**仍然不允许出现重复元素**，所以“新值已存在”那一条必须检查。

| `buildIn` / `build`（`TODO 3`） | `build` 检查 `_root` 非空与否并置 `i = 0`，`buildIn` 按引用推进 `i` 从字符串读字符，用 `new BinNode{ch, nullptr, nullptr}` 建节点并递归接 `lc`、`rc` | 树为空时建树成功（含空串、全 `'#'`）返回 `true`；`_root` 已非空时拒绝返回 `false` 且原树不动 |
| `remove`（`TODO 4`） | 复用 `search` 取槽，用教师提供的 `HasChild` 宏判定是否叶子 | 是叶子则 `delete` 节点并把槽写成 `nullptr` 返回 `true`；元素不存在或非叶子返回 `false`、树不变 |
| `update`（`TODO 5`） | 两次复用 `search`（一次查旧值取槽、一次查新值判重复） | 两个值相等、旧值不存在、新值已存在时返回 `false` 不改树；否则原地写 `slot->data = newValue` 返回 `true` |

回答下面三个问题，每题两三句话：

1. 为什么 `search` 返回 `BinNodePosi&` 而不是 `BinNodePosi`？`remove` 中如何利用这个引用？

   > 删除一片叶子，真正要改的是"父节点里存放指向它的那个指针"（`_root`、`lc` 或 `rc`）。返回引用拿到的就是这个变量本身：`remove` 里 `delete slot; slot = nullptr;` 直接把父节点那格写空，接链关系随即更新。若只返回节点指针的副本，`remove` 手里只有一个局部拷贝，`delete` 之后没有任何办法改到父节点的孩子指针，野指针就会留在树里。

2. 树为空时 `search(e)` 返回什么？为什么它仍然是一个合法的引用？

   > 空树时 `searchIn` 第一次进入就在 `_root` 这格槽上发现它是空指针，立刻返回 `_root` 的引用本身。这个引用绑定的是类的数据成员 `_root`，不是什么临时值或已释放的内存，所以是合法左值，只是它此刻的内容为 `nullptr`，表示"落空"。测试 1（empty tree）验证的正是这一点。

3. 如果把 `remove` 写成只 `delete` 节点、忘记把槽置空，会发生什么？请结合"父节点还指着已释放节点"说明。

   > 该节点占用的内存已归还给堆，但 `_root` 或父节点的 `lc`/`rc` 仍保存着原来的地址：任何后续的 `search`、遍历都会顺着这个悬垂指针去读 `->data`、`->lc`、`->rc`，读到的是不确定的内容，可能输出乱码结果，也可能把垃圾地址当孩子继续走导致崩溃；若再次删到同一元素还会对同一地址重复 `delete`，破坏堆结构。测试 6（remove leaf）专门检查了删除后 `B->lc` 变为 `nullptr`，就是防止漏掉置空这一步。

### 6.2 建树过程追踪

| 读到的元素 | 动作 | 执行后的 i |
| :--- | :--- | :---: |
| `A` | 建根节点 `A`，先递归去建它的左子树 | 1 |
| `B` | 建节点 `B` 接在 `A->lc`，先递归建 `B` 的左子树 | 2 |
| `D` | 建叶子 `D` 接在 `B->lc`，递归建 `D` 的左子树 | 3 |
| `#`（第 1 个） | 返回 `nullptr`：`D` 无左孩子 | 4 |
| `#`（第 2 个） | 返回 `nullptr`：`D` 无右孩子，`D` 完成，回到 `B` 继续建右子树 | 5 |
| `E` | 建节点 `E` 接在 `B->rc`，递归建 `E` 的左子树 | 6 |

| `#`（第 4 个） | `E` 无右孩子，左子树全部完成，回到 `A` 建右子树 | 8 |
| `C` | 建节点 `C` 接在 `A->rc`，递归建 `C` 的左子树 | 9 |
| `#`（第 5 个） | 返回 `nullptr`：`C` 无左孩子 | 10 |
| `F` | 建叶子 `F` 接在 `C->rc`，递归建 `F` 的左子树 | 11 |
| `#`（第 6 个） | 返回 `nullptr`：`F` 无左孩子 | 12 |
| `#`（第 7 个） | 返回 `nullptr`：`F` 无右孩子，`F`、`C`、`A` 依次完成，建树结束 | 13 |

然后回答：

1. 按这个序列建出的树画出来（用文字或字符图均可），并指出根节点的元素与叶子节点。

   > ```text
   >           A
   >          / \
   >         B   C
   >        / \    \
   >       D   E    F
   > ```
   >
   > 根节点元素是 `A`；叶子节点是 `D`、`E`、`F`（`B` 有两个孩子，是内部节点；`C` 只有右孩子 `F`）。与教师测试第 3、4 组建出的 6 节点树一致，三种遍历核对结果为 `ABDECF`、`DBEACF`、`DEBFCA`。

2. 如果序列写成 `"ABD##E##C###"`（把 `F` 换成 `#`），树会变成什么样？哪几个节点消失？

   > 读到 `C` 之后的三连 `#`：第一个说明 `C` 无左孩子，第二个说明 `C` 无右孩子，`C` 由此成为叶子，第三个说明 `A` 的右子树之外再无内容。变化只有一个节点：`F` 消失，树变为 `A(B(D, E), C(⊥, ⊥))`，其余 5 个节点的形状不变。

3. 如果序列少写一个 `#`（字符串变短），建树会怎样？为什么 `buildIn` 要先判断 `'\0'`？

   > 例如写成 `"ABD##E##C#F#"`：建到 `F` 的右子树时 `seq[i]` 已经是 `'\0'`，此前若不先判断就会越过字符串末尾继续读内存（越界，读到的内容不确定）。先判 `'\0'` 后，"没字符了"被当作"这棵子树为空"返回 `nullptr`，而且这一分支不再推进 `i`，不会越界。后果是缺的那格被空子树悄悄补齐：`build` 照样返回 `true`，建出的树比完整序列矮一点（`F` 变成右孩子缺失），整棵树不会崩溃——我用这两个不完整序列实际运行验证过，详见 6.6。

### 6.3 删除过程追踪

先填写三种情况的处理方式：

| 情况 | 判断条件 | 处理 | 返回值 |
| :--- | :--- | :--- | :--- |
| 元素不存在 | `search(e)` 返回的槽内容为 `nullptr` | 什么都不做，原树原样保留 | `false` |
| 不是叶子 | 槽非空且 `HasChild(*slot)` 为真 | 什么都不做，原树原样保留（本实验不处理内部节点） | `false` |
| 是叶子 | 槽非空且 `HasChild(*slot)` 为假 | `delete` 这个节点，再把这一格槽写成 `nullptr` | `true` |

再以 6.2 建出的树为起点，依次执行下列删除，逐行填写：

| 被删元素 | 属于哪种情况 | 删后该位置的内容 | 删除后整棵树的先序序列 |
| :--- | :--- | :--- | :--- |
| `D` | 是叶子 | `nullptr`（`B->lc` 被置空，`B` 变成只有右孩子） | `ABECF` |
| `B` | 不是叶子（还有右孩子 `E`） | 仍是节点 `B`，未删除 | `ABECF` |
| `A` | 不是叶子（两棵子树都还在） | 仍是节点 `A`，未删除 | `ABECF` |
| `F` | 是叶子 | `nullptr`（`C->rc` 被置空，`C` 变成叶子） | `ABEC` |
| 再删一次 `F` | 元素不存在（那格槽已经是 `nullptr`） | 仍是 `nullptr`，树不变 | `ABEC` |

然后回答：

1. 为什么无序树不能像有序树那样用“右子树最小者”顶替被删节点？

   > “右子树最小者”这一说法依赖有序性：只有树按“左小右大”组织，“最小”者才存在、且它顶替被删元素后恰好填补空位、不破坏任何次序。无序树里元素与位置的大小关系没有任何约定，既不存在唯一的“最小者”，随便挑一个节点顶上来也谈不上“合适”；而且被删的是内部节点时，它的孩子子树怎么安置没有任何规律可依。为避开这些没有定义的问题，本实验干脆只允许删叶子——叶子不带子树，摘掉它不丢失任何接链信息。

2. 删除一片叶子时，`search` 返回的那个引用起了什么作用？如果只拿到节点指针会怎样？

   > 那个引用就是“父节点里保存这片叶子地址的那一格”（`_root`、`lc` 或 `rc` 之一）：`delete` 之后用 `slot = nullptr` 把这格写空，等于没有 `parent` 成员也完成了摘链。若只拿到节点指针的副本，`delete` 后就再也无法访问父节点里那个指针，它永远指向已释放的内存，后续遍历必踩野指针。

3. 如果要求必须能删内部节点，至少需要额外的什么信息或什么约定？举一种可行做法并说明代价。

   > 至少要约定“被删节点的孩子们去哪”。一种可行做法是**删去以 `e` 为根的整棵子树**：照常 `search` 取槽（槽的引用保证能摘链），先按“先左右、后根”的后序逐一 `delete` 该子树的所有节点，最后把槽置空即可，不需要任何新成员。代价是：该子树中除 `e` 之外的所有合法元素也一起被删除（信息损失），且释放需 O(该子树规模) 的时间。若想保住其余元素，就得仿照有序树用某个后代顶替接链——那要么给节点增加 `parent` 指针，要么用指针槽引用递归下探改写接链，实现代价和代码复杂度都明显更高。

### 6.4 复杂度

按本实验的实现分析；视一次元素比较、一次指针赋值、一次节点申请与释放为常数开销。令 `n` 为树中节点数，`h` 为树高。

| 项目 | 复杂度 | 简要理由 |
| :--- | :--- | :--- |
| `build()` 的时间（按 `n`） | Θ(n) | 序列中每个字符（元素或 `'#'`）恰好被读一次，每个节点恰好被 `new` 一次，读过即不再回头，总工作量与节点数成正比 |
| `buildIn()` 的递归深度（按 `h`） | Θ(h) | 递归每深入一层就对应树中更深的一层，深度等于树高；完全树约 Θ(log n)，单链树退化到 Θ(n) |
| `search()` 最坏情况的时间 | Θ(n) | 无序性导致每层比较一次不能排除任何一侧，目标位于最后访问的节点（或根本不存在）时，左、右两支都要走完整棵树的 n 个节点 |
| `search()` 在平衡的树上平均要访问多少个节点 | 约 n/2 个 | 遍历按固定次序扫描，查找命中位置在序列中“等可能”分布，期望排名约为一半；量级仍是 Θ(n)，与树高 h 无关——平衡并不会把无序树的查找加速到 O(log n) |
| `remove()` 的时间 | Θ(n) | 开销集中在开头那次 `search` 的整树遍历；命中之后判叶子、`delete`、槽置空各是 O(1) |
| `update()` 的时间 | Θ(n) | 需要做两次 `search`（先找旧值所在槽、再确认新值不存在），仍是线性；真正改写 `data` 只是 O(1) |
| 存放 `n` 个元素的树占用的空间 | Θ(n) | 每个节点固定三个字段（一个 `char` 加两个指针），n 个节点即 Θ(n)，树再无其他数据成员 |

### 6.5 讨论

用自己的话回答，每题两三句话：

1. 本实验为什么“查找必须遍历”？请举一个**必须**借助遍历才能完成的任务，并说明原因。

   > 树没有任何有序性，比较一次不能排除任何一侧子树，目标可能藏在任何位置，唯一保证正确的方法就是把所有节点都看一遍——这正是遍历。必须借助遍历才能完成的任务例如“统计全树是否出现重复元素”（或“把所有叶子列出来”）：这类问题的答案与**全体**节点有关，不是问“某个元素在哪”，即便树是有序的也只能全树走一遍，无序树就更没有捷径。

2. 为什么无序树只允许删叶子？对照有序树的三种删除情况，说明差别来自哪里。

   > 有序树删叶子只需摘链；删单孩子节点可以把孩子顶上来；删两孩子节点有“中序后继”这个确定的接替者，接上后次序不乱。这三招全部依赖“元素与位置有大小关系”这一前提。无序树里：单孩子节点本来也能“孩子顶上来”，但两孩子节点既没有唯一的接替者、也没有任何次序可以校验接替是否正确，随便定一个规则（如“用右孩子顶替”）虽然技术上可行，却与本实验“无序”的语义冲突且要处理悬空的左子树。为把练习聚焦在“指针槽引用摘链”这一个要点上，题目约定只删叶子——叶子对象最简单，摘掉它不牵连任何子树。

3. `update` 在无序树里可以直接改 `data`，在有序树里却必须“删旧插新”。请举例说明有序树直接改会破坏什么。

   > 例如 BST `50(30, 60(55, 70))`，把 `60` 改成 `25`：`25` 位于根的右子树，却比根 `50` 小，也比自己的左孩子 `55` 小——“左小右大”全部被破坏。此时再 `search(25)`，按比较规则下降会先进左子树，反而查不到它，树从“能按 O(h) 查找”退化成“就算全树遍历也得靠运气”。有序树因此必须删旧插新，让元素回到按大小应待的位置；无序树没有要维持的次序，原地改写完全无害，但“不出现重复元素”的约定仍要靠一次 `search` 检查来守住。

4. 先序扩展序列为什么能唯一确定一棵二叉树？如果只给中序序列、或只给先序序列，还能不能唯一确定？

   > 扩展序列把“空子树”也用 `'#'` 写了出来，相当于给含空指针的完整结构拍了照：读入时每个位置要么建节点、要么落成空，根、左、右的递归次序固定，每个字符的归属唯一，因此还原出的树唯一。只给中序序列不能唯一确定：如 `BA` 既可以是 `A(左B, ⊥)`，也可以是 `B(⊥, 右A)`。只给不带扩展的先序同样不能：Lab11 已验证，先序 `AB` 既可对应 `A(左B, ⊥)`，也可对应 `A(⊥, 右B)`，两种树先序相同——差别正在于“空位没写出来”。

5. 本次没有实现析构函数，程序结束时树上剩余的节点不会被释放。这会在什么场景下成为问题？如果要补上，可以怎样写（说明思路即可，不必给出代码）？

   > 在进程长期常驻、树被反复建删的场景（服务程序、测试框架、被反复重建的缓存）里，每轮遗留的节点都无法回收，内存占用只增不减，最终可能耗尽内存导致程序或系统变慢甚至崩溃，排序与查错都很困难。补法：给 `BinTree` 写析构 `~BinTree()`，思路与 Lab11 的 `destroyTree` 一致——按“先左右子树、后根”的后序递归 `delete`（先释放子树时根还在，能顺着 `lc`/`rc` 找到孩子；最后 `delete _root` 并将其置空）。如果不允许加成员函数，也可以只在 `main` 里显式调用这样一个后序释放函数，效果相同。
